# SignMail

A mobile-first Flutter email client designed around approachable S/MIME signing.

## Current status

**Phase 0 / UI prototype.** This project currently contains a navigable interface prototype only. It does not connect to mail servers, import certificates, cryptographically sign messages, synchronise an inbox, or send email. The UI intentionally labels those actions as unavailable.

## Toolchain

- Flutter stable (use the current stable release supported by your chosen build environment)
- Dart version supplied by that Flutter SDK
- Android target first
- Git + GitHub for source control
- Cloud Android build (e.g. GitHub Actions) if building locally on the phone proves unreliable

## Proposed libraries (evaluate before production use)

- `enough_mail`: candidate IMAP/SMTP/MIME library. Verify provider discovery, XOAUTH2 needs, attachment handling, TLS behavior, and maintenance before shipping.
- `flutter_secure_storage`: protect app secrets and small credential values; not a replacement for a dedicated private-key design.
- `file_picker`: select user-provided `.p12` / `.pfx` files using Android's document picker.
- `local_auth`: optional app-lock UX; not the only protection for keys.
- Bouncy Castle on Android (via a small Kotlin bridge) is the leading candidate for CMS/S/MIME operations. Confirm current Android compatibility, license, API surface, and tests before implementation.

Do not use this prototype to send real confidential mail.

## First run

1. Install Flutter stable in your chosen build environment.
2. Create a Flutter project named `signmail` or place these files into a generated Flutter project.
3. From the project root run:

   ```sh
   flutter pub get
   flutter analyze
   flutter run
   ```

4. For a release APK after the project builds successfully:

   ```sh
   flutter build apk --release
   ```

The native `android/` directory is normally generated by `flutter create`; keep the generated Gradle wrapper and Android project files rather than hand-writing them.

## Security invariants

1. Never silently send unsigned if signing is required by the user.
2. Never claim a message is signed until CMS signing succeeds and the outgoing MIME structure is verified.
3. Never upload private keys or PKCS#12 passwords to a SignMail-operated server.
4. Use TLS for IMAP/SMTP; do not disable certificate validation to work around connection errors.
5. Keep credentials out of logs, crash reports, analytics and backups.
6. Validate the signing certificate identity against the sender address, validity dates, key usage and chain policy.
7. Test signatures with an independent implementation and multiple mail clients.

## Suggested project phases

- P0: UI prototype (included)
- P1: build pipeline, app structure, linting and tests
- P2: secure account configuration and SMTP send of unsigned test messages
- P3: certificate import, identity validation and secure key lifecycle
- P4: CMS detached/opaque S/MIME signing and independent verification
- P5: IMAP inbox, MIME parsing, attachments, folders and sync
- P6: certificate/signature verification UI and strict failure policy
- P7: provider interoperability, security review, accessibility and release hardening
